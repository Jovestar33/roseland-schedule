September 18, 2026. **Local connected same-schema fallback rehearsal; production D09, hosted RPO/RTO and excluded-feature deltas pending.** Reviewed application: B13 `4121426`, following B12 `cf4b0ee`. No actual schedules, accounts, mail, hosted configuration or deployment changed. The separate B11 preview remains pinned and preserved.

## Result

Two fresh connected destinations recovered the complete captured current database with genuine Auth/MFA and the reviewed application. The second reconstruction used saved files, preserved the new destination browser edit as schedule version 3, and passed the same access checks. Before each activation, every row in all 98 captured non-system tables was compared exactly, including empty tables. The final captured generation contains 664 records. No unexplained missing, extra or mismatched rows remained. Complete documents, versions/history, identities/factors/sessions, membership/restrictions, templates/provenance, snapshots, presentation, live/revoked Client links, pending-deletion state, audit/outbox, receipts and migration history are covered by the inventory. Stores that are empty are explicitly shown as zero; this does not claim nonempty workflow execution for every table.

The full database dump is paired with roles/password material, database/role settings, effective ownership/default grants/RLS, function definitions and settings, extension versions, sequences, and captured service images/configuration/credentials/templates. Column order/types/defaults/nullability, constraints, indexes, views, enums, triggers and event triggers also match logically. PostgreSQL compacts dropped physical column slots during logical restore; the comparison preserves remaining column order but ignores those obsolete slot gaps. Equivalent ACL ordering and implicit owner-only ACL defaults are normalized explicitly; real grants are retained and verified.

Full artifacts are owner-only under `/private/tmp/roseland-b14-artifacts` (directory 0700, files 0600). They contain fictional credentials and are deliberately excluded from Git. The committed evidence contains hashes, counts, reports and browser text only. A known-secret scan of committed evidence passed; it is not a general historical entropy scan.

## Execution and evidence

- A new B14 fixture used genuine local identities and TOTP, separate from B13. The complete schedule document came from B12's original `alpha-new` capture bytes. B12's original capture/mapping evidence remains intact; this was not a new import of every B12 record into the independent Auth fixture. E10's canonical hashing and validation helpers are reused, with a larger full-database boundary.
- Baseline capture preceded genuine newer schedule, CMS, template, snapshot, restriction, membership and pending-deletion operations. A previously revoked genuine session and revoked share were retained as denial checks. API/Auth/gateway services were stopped and residual application transactions drained before each capture. The original source remained stopped after the final source capture.
- Recovery generations and table-change journals are immutable and predecessor-linked. These are complete-state snapshots with an ordered journal of changed table hashes/counts, **not WAL replay, PITR or a continuously captured incremental backup**. Wrong predecessors, reordered generations, missing config/grant files and a semantically missing session hook are refused. An exact lost-ack retry returns the recorded restore result without replay. A newer destination edit blocks an older restore and remains unchanged.
- An injected failure after real data loading rolled back the restore transaction to no application tables. Failed databases/artifacts are retained. Role restoration happens on the isolated frozen cluster before the database-load transaction; cluster-wide role changes are not part of that rollback. No active or shared cluster is a permitted destination.
- Seven explicit refusal/retry gates pass. Sixteen connected readback checks pass on each destination: genuine password + original TOTP, owner AAL1 denial, complete owner/Editor documents/version, suspended member and cross-tenant denial, newest template/snapshot/CMS, pending-deletion freeze, revoked session/link, Client allowlist, application route, and original-source write denial. See `gates.json`, both `*-readback.json` files, and `newer-destination-protection.json`.
- Browser evidence confirms genuine Editor sign-in after each restore, current organization labels, version 2 source content, a new browser save as version 3 on generation 1, then that saved version 3/newest edit after reopening generation 2. Batch test tabs were closed afterward.

Successful restore-and-reconcile intervals were **6.796 seconds** and **6.758 seconds**. These measure frozen destination role setup, transactional load, row/catalog reconciliation, database promotion and settings restoration. They exclude stack initialization, source capture, failed attempts, activation, browser inspection and operator decisions. `timing.json` separately records elapsed time from the final capture manifest to passing connected readback, including intervening work. Neither measure establishes hosted RPO/RTO or selects the actual production fallback.

## Failures found and corrected

The retained failures are part of the evidence. The first edit harness used the wrong version-field name; no edit occurred before correction. Plain `pg_dump` omitted bootstrap schema grants and modified extension search-path/security-definer attributes; reconciliation rejected activation until a supplemental capture restored them. One supplemental signature needed fully qualified enum types. List-valued role settings required PostgreSQL's `SET ... FROM CURRENT` semantics rather than treating the list as one quoted identifier. The ACL injection test needed to restore the original grantor. The gateway's captured startup command also needed destination host mapping; the first connected readback returned a local routing failure until corrected. A redundant activation attempt correctly refused already-running services. None of these failures was relabeled as a pass.

The second complete reconstruction ran through the corrected path with matching data, logical schema, roles/settings/grants, required session hook, service images, captured Auth keys and explicitly mapped local origins. Only the current reconciled destination exposed an API; the original source and then generation 1 remained stopped. Batch cleanup stops all B13/B14 app/API/Auth/database/mail services while retaining their volumes and failed generations. It does not stop the B11 preview.

## Operator procedure for this bounded rehearsal

1. Use only the allowlisted unlinked fictional projects in `scripts/recovery/b14.py`. Start from the reviewed application/build and independent dependencies. Verify available ports; preserve the B11 preview. Never point these scripts at a hosted or real-data project.
2. Save the live service status privately while the source runs. Freeze source gateway/Auth/REST, drain their database sessions, then capture a new uniquely named generation. Keep the prior generation unchanged. Preserve the manifest, journal, complete SQL, role/settings/supplement, catalog, service configuration and templates together.
3. Validate the entire predecessor chain. Initialize a fresh same-image destination with no application migrations. Stop its exposed services. Run `restore` with the ordered generation names; it restores into a separate transactional database, compares all rows and catalog material, retains the pristine database, and writes a private receipt. A failed generation must be inspected and retained before retrying under a new name; never overwrite newer target state.
4. Run the service activation helper only for the exact reconciled generation. It requires the saved keys, hook, role/database settings, logical structure and matching images. It reconstructs only Auth/REST/gateway configuration and maps local origins/hosts explicitly. Retain replaced containers. Do not treat a service-start command as successful recovery: require connected password/MFA, denial and application checks.
5. Keep the predecessor source stopped. Verify the newest application document, history-dependent stores and revoked/frozen boundaries. After a new destination save, prove older restore refusal, freeze/capture that destination, and reconstruct a second fresh stack from the files. Verify the newest edit again.
6. Retain the private artifacts and volumes; stop only batch-owned services. Confirm the pinned preview remains reachable. Production custody, encryption/retention, backup scheduling, mail/session handling, restore reapplication after future purge, operational ownership and measured hosted recovery objectives need separate approval and evidence.
