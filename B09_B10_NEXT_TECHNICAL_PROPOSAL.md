## B09-A: ordinary enrollment and organization policy

### Minimal state and API

1. Add `private.organization_mfa_policy`: organization ID, version, required optional roles, updated actor/time. Required-role values are `admin`, `organizer`, `editor`, `viewer`; default is an empty set. Organization Super Admin (`owner`) and active Platform Super Admin requirements cannot be disabled by this setting. Enable RLS, revoke direct client table access and add only narrowly granted RPCs through a forward migration.
2. Add `get_my_mfa_status()` and paginated `list_my_organization_access(after_id?, organization_id?)`. Return only the caller's assurance/enrollment state and their own active organization memberships: ID, name, role, MFA-required flag and access state. No other member directory, platform designation detail or schedule data. These bootstrap reads remain available after valid first-factor authentication, subject to live-session/ban checks, including when terms or MFA completion is pending. Existing terms/deadline/activity controls retain their narrow exceptions.
3. Add `read_organization_mfa_policy(organization_id)` and `save_organization_mfa_policy(organization_id, request_id, expected_version, required_roles)`. Reading requires admitted active membership; saving requires active Organization Super Admin/Admin Settings authority, existing effective restrictions, an active writable organization and recent TOTP verification within 30 minutes. Identity and `aal`/TOTP `amr` come from the verified PostgREST JWT, never request JSON. A small private recent-MFA helper serves these new authenticated RPCs; existing server workflow checks remain intact.
4. Reuse actor-bound fingerprint/receipt behavior from presentation settings: identical retry returns the original confirmation, changed payload under the same request ID conflicts, stale version requires review. Recheck current authority before returning a receipt. Policy update, receipt and non-secret audit commit together under the organization policy lock.
5. Use provider `mfa.enroll({factorType:'totp'})`, `listFactors()`, `getAuthenticatorAssuranceLevel()` and `challengeAndVerify({factorId,code})`. QR/secret/code stay in component memory, never durable journals, audit or logs. Support enrolling a first factor and challenging an existing verified factor. Do not remove/replace verified factors or bulk-clean other pending enrollments. If an abandoned unverified enrollment cannot be resumed without its secret, offer a fresh enrollment with bounded cleanup only of the attempt this component created.

### Enforcement and user behavior

- **Account factor versus organization policy:** a verified factor belongs to the account. Fresh AAL1 sessions on an enrolled account must challenge before protected application access. An active Platform Super Admin must enroll/challenge before protected platform access. Organization Super Admins must enroll/challenge before accessing their organization; optional-role requirements apply at the target organization's boundary, not to unrelated organizations of an unenrolled user. For organization policy, any matching active production role in that organization makes MFA required there; suspended production roles do not count. Once enrolled, the account challenge rule applies across organizations.
- Add a private organization-admission predicate derived from live memberships/policy plus trusted user assurance. Compose it into all tenant read/write boundaries, including helpers used by direct-table RLS and security-definer RPCs; passing an arbitrary organization header cannot select policy. Existing service workflows require their separately verified actor context. A missing assertion fails closed. Do not weaken schedule restrictions or allow discovery endpoints to expose protected contents.
- Role/policy changes take effect on the next protected request without waiting for refreshed role claims. Authorization-changing writes and ordinary writes use the existing organization lock order and recheck after locking. Already admitted transactions may finish under the B08 boundary. Ordinary saves require sufficient assurance, not a new code for every save; only explicitly sensitive operations use the recent-verification window.
- UI states: `checking → enroll_required | challenge_required → ready`, plus a recoverable error. Add Account Security and an organization Security setting with role toggles; fixed required roles are explanatory text. Use a dedicated machine reason such as `mfa_required` with a 403 response, not the existing terms-only 428 handler. RLS-filtered responses are resolved through the narrow status RPC instead of presenting a protected organization as deleted.
- After verification, refresh the verified session/access status and resume the same actor's retained draft or exact pending attempt. Never automatically resubmit a stale/conflicting write. Policy changes from another tab gate the affected panel without discarding drafts; changing identity retains the existing discard/isolation behavior. Password recovery alone does not satisfy an enrolled factor.

**Focused acceptance:** first enrollment and next-login challenge; wrong-code recovery; optional unenrolled ordinary use; mandatory owner/platform access and one organization-policy case; direct API denial and unrelated-organization scope; stale policy version/exact retry; role/policy change taking effect on the next request; same-actor draft return and one retained sensitive-action retry. Check relevant existing account, invitation, permission and editor regressions once, plus build/types. Use fictional local accounts and the existing stack.

**Exact stop:** commit the ordinary gate, policy, UI and focused evidence; stop owned services, preserve volumes and drafts. Do not include factor removal/replacement, exceptional recovery, provider/race investigation, B10 implementation or hosted changes. Label this B09-A accepted locally, not all of B09 complete.

## B10-A: scoped membership suspension and reinstatement

**Minimal API/state:** add a monotonically increasing membership revision; `list_organization_members(organization_id, after_id?)` returns a bounded in-org administration list with role/status/revision and allowed actions only to authorized leadership. Add `set_organization_member_status(organization_id, membership_id, expected_revision, request_id, next_status, confirmed, reason)` for explicit active/suspended transitions as an authenticated RPC with the same live-session, recent-TOTP, actor-bound receipt and audit conventions. The target comes from the membership row in the specified organization, never a caller-supplied role. UI lives in Organization Settings → Members, with a named-target confirmation for peer Super Admins. No global Auth ban, account deletion or role transfer. Reinstatement preserves the stored prior role and all independent restrictions; it changes only this organization membership, never invalidated invitations or other memberships.

**Authority/transaction:** Admins may suspend only lower-role members within effective authority; only an Organization Super Admin may suspend an Admin or a peer Super Admin. Reinstatement uses exactly the same role authority, rechecked against the current actor and the target’s retained role. Exclude platform-operator target changes from this slice. Under the existing organization policy lock, reread actor/target authority, expected revision and active-holder count before transition. Peer suspension requires explicit confirmation and must leave at least one active Organization Super Admin with an enabled account. Cover status/role/delete paths capable of removing an active holder with the same invariant, so it cannot be bypassed through another existing writer; this adds no new demotion/promotion operation. Reject stale requests, prevent self-targeting in this peer workflow, and do not infer transfer authority.

Commit an explicitly authorized `active → suspended` or `suspended → active` transition, revision, receipt, audit and notification intent atomically. Existing invitation invalidation runs only on suspension; reinstatement cannot recreate those invitations. An exact retry returns the original outcome without another event; a newly submitted request for a membership already in the requested state returns an explicit unchanged result after current authorization, without duplicate notification. Subsequent organization access is denied; other organizations, documents and history are preserved. Already admitted requests retain the established boundary. Only the explicit reinstatement operation may unsuspend a member; invitation acceptance, deletion cancellation and a suspension retry may not do so.

**Small notification addition:** private `administration_notification_outbox` with event ID, recipient, organization, non-secret template payload, delivery state/attempts and a unique event/recipient key. Queue affected-member notification for suspension or reinstatement; a local-only adapter delivers to the mail sink, records failures and supports retry. Do not put delivery inside the authorization transaction or roll back suspension because mail is unavailable. Surface pending/failed delivery to authorized leadership. No real-email dispatch or new messaging framework.

**Focused acceptance:** ordinary member suspension and reinstatement with the retained role/restrictions; lower-role/peer authority and wrong-tenant denial for both transitions; no global-ban, independent production/schedule restriction, unrelated-membership or invitation changes; Admin/peer authority denial, wrong-org and restricted-actor denial; peer confirmation and affected-user mail-sink notification; two competing final-holder operations leave an active holder; subsequent access denial and invitation non-reactivation; exact retry/stale revision; failed notification retry without duplicate intent. Relevant permission/invitation regressions once; no B08 token-race suite.

**Exact stop:** locally accepted scoped suspension/reinstatement and notification delivery evidence. Update the source contract that previously deferred reinstatement; keep invitation-based reactivation prohibited. No B10-B deletion or exceptional recovery implementation.

## B10-B: 30-day recoverable organization deletion

**Minimal state:** private `organization_lifecycle` stores organization ID, version, deletion request ID, requesting actor, requested time, cancellation deadline and cancellation actor/time. Reuse immutable receipts/audit for each lifecycle operation. Keep `organizations.deleted_at` null during the recovery window so existing reads can remain available; prohibit direct client changes to deletion/lifecycle fields. Lifecycle authority cannot be obtained through the current broad organization-settings update policy.

| State/transition | Contract |
|---|---|
| `active → pending_deletion` | Active Organization Super Admin, recent TOTP and explicit named-organization confirmation. Set deadline to request time plus 30 days, using database time. Preserve memberships, restrictions, documents and history. Notify all organization Super Admins. |
| Pending access | Existing effective read/history/export only; paused ordinary writes. Suspended members stay denied. Show deadline and cancellation control only to an eligible active Super Admin. Account security/session controls and narrowly authorized cancellation remain available. |
| `pending_deletion → active` | Any active Organization Super Admin may cancel while database time is strictly before the deadline. Preserve individual suspensions/restrictions; notify all organization Super Admins. Do not recreate invitations invalidated by suspension. |
| Deadline reached | Derive `awaiting_purge`; retain the same frozen access boundary until a separately approved purge process runs. No ordinary cancellation after the deadline, no automatic physical deletion in this slice, and no promise that all stored copies disappear on day 30. |

**API/UI:** `read_organization_lifecycle(organization_id)`, `request_organization_deletion(organization_id, request_id, expected_version, confirmed)` and `cancel_organization_deletion(organization_id, request_id, expected_version)`. Use authenticated RPCs and the same private recent-MFA helper, authority checks and actor-bound exact receipts. Return state/version/deadline and allowed actions; add an Organization Settings deletion panel and a persistent read-only banner. Billing/subscription is a separate workflow.

**Serialization and coverage:** acquire the organization policy lock before authority, deadline and version checks. Exact previously committed retries return their recorded result rather than extending the window; changed/stale requests conflict. Cancellation checks the clock after acquiring the lock, and any eventual purge worker must acquire that same lock and recheck state/deadline. Add a shared organization-writable guard to direct-table triggers/RLS and RPC writes for schedules, hierarchy, copy/transfer/import, snapshots (including automatic capture and purge), templates, presentation, restrictions/roles, invitations/acceptance and ordinary membership changes. Check every affected organization for cross-scope operations. Cancellation and account-security exceptions are explicit, not blanket service-role bypasses. Preserve unsaved local drafts; pause autosave/capture and require revalidation before saving after cancellation.

**Focused acceptance:** request and exact retry; existing allowed read/export while pending, denied export still denied, suspended member still denied; representative direct write and each existing write family through a focused shared-guard contract; cancellation by a different active Super Admin with restrictions/suspensions unchanged; stale revision; before/at-deadline behavior under a controlled clock and serialized cancellation/expiry check; notification delivery/retry. Verify no physical deletion and no billing changes. Relevant existing lifecycle, snapshot, permissions and editor checks once.

**Exact stop:** locally accepted request/read-only/cancel behavior and notifications, with an explicit pending operational purge item. No purge scheduler, permanent erasure, hosted migration, real organization changes or billing calls. Do not label operational B10 deletion complete.

## Separately reviewed exceptional and operational boundaries

**Exceptional factor loss — approved authority and proof, September 18:** use a human-reviewed case scoped to the organization and target account. Organization Admins or Organization Super Admins may approve recovery for Production Organizers, Editors and Viewers; only an Organization Super Admin may approve recovery for an Organization Admin or Organization Super Admin. A production assignment cannot lower the target's organization rank for this decision. Verify identity through a previously known phone number or in person; email alone is insufficient. Record the approving actor, verification method/time/outcome and short reason without collecting identity-document copies by default. Notify the affected user. When all organization Super Admins are locked out, escalate to the Platform Super Admin and notify organization Super Admins. Denied/unverifiable cases stay denied; no automatic tenant-access grace session.

The ordinary proof/reviewer choice is now settled and must not be re-asked. Require recent MFA for the authorized assisting Admin/Super Admin as part of the later sensitive-operation contract; no self-approval. Before any account-wide operation, privately detect cross-organization membership or platform designation and route to restricted platform review without revealing other tenants. **The remaining narrow technical boundary** is the approval-to-execution mechanism and proven revocation/retry behavior, plus the authority/impact contract for cross-organization or platform-designated targets. The former suggestion of a second reviewer is not an approved requirement for ordinary recovery; any additional review for account-wide exceptional cases belongs in that separate contract. Platform Super Admin self-recovery and routine authenticator replacement remain outside this approval.

The later technical contract must prove a one-use, expiring, actor/target-bound recovery authorization; replacement-only access; old-factor removal and affected-session revocation; fresh login; exact retry/audit and mail-sink notification failure handling. Do not promise provider capability until reviewed in that separately dispatched task. No factor-reset API or provider investigation is part of this proposal or B09-A.

**Permanent purge — concrete operational recommendation for later release review:** produce a dependency manifest for tenant rows, documents/history, snapshots/trash, templates, share artifacts, files/blobs, audit/receipts and any external copies. Define deletion order, referential checks, resumable operation identity, dry-run inventory, completion evidence and failed-step retry. Cross-tenant accounts/factors and retained shared references must not be blindly deleted with the organization. Confirm actual provider backup retention/restore behavior and any applicable retention holds; document when data ceases to be available in the live app versus aging out of backups. A restored backup must reapply completed deletion records before tenant access resumes. Select and disclose retention exceptions and operational ownership before enabling a purge worker. These are release/operations review items, not reasons to reopen the approved 30-day product window or block B09-A.
